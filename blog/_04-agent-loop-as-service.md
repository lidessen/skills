# Agent Loop as a Service

在业务系统里加入一个 AI 功能，可以从接入模型开始。但要让它持续运行，项目还要处理工具调用、上下文、权限、用户交互、任务排队、失败恢复，以及费用和审计。

这些工作中，有些必须根据业务规则实现，有些却会在每个项目里重复建设。Agent Loop as a Service（本文简称 AaaS）希望把后者做成公共服务：业务提供任务、上下文和允许使用的工具，服务负责执行，并让业务能够查询进度、参与交互和获取结果。

本文介绍这一产品设想，仍处于草稿阶段。

## 1. 业务为什么需要 AaaS

AI 能力进入业务系统，至少有两种常见形态。

一种是具体的 AI 任务，例如生成摘要、分类、自动分配。它们通常由业务事件触发，完成后把结果交给已有流程。在目前的实践中，我观察到，即使是分类任务，Agent Loop 的表现也比直接调用 LLM 更好。这个判断仍需要补充案例、比较条件和效果记录，才能说明适用范围。

另一种是 Assistant。用户连续表达需求，Agent 根据已有对话和执行反馈继续工作，必要时提问或申请批准。我倾向于把它理解为上下文连续的多轮 Agent 任务。

这两种形态都需要执行能力，但对交互和上下文的要求不同。AaaS 的价值在于让它们共用一套执行服务：后台任务不必为使用 Agent 先构建聊天系统，Assistant 也不必独自实现队列、运行管理和费用追踪。

业务仍然要定义什么结果有用、哪些数据可读、哪些操作可以执行。公共服务负责在执行中落实这些要求。

## 2. 为什么以 Agent Loop 为执行单位

这里的 Loop 指一次任务中的执行循环：模型接收指令和上下文，选择直接回答或调用工具；工具结果回到模型后，模型决定继续行动还是结束。Loop 可以只调用一次模型，也可以发生多次工具往返，不要求每个任务都探索或自检。

选择这个执行单位，是为了容纳任务中途才出现的信息。自动分配任务可能需要先查候选团队，再根据查询结果补充条件；Assistant 可能需要澄清用户意图，再决定调用哪个业务接口。这些工作都需要把反馈带回决策过程。业务可以给出目标和可用能力，而不必为每一种反馈提前写好执行路径。

三种形式各有适用范围：

| 形式          | 适用条件                       | 主要代价                                     |
| ------------- | ------------------------------ | -------------------------------------------- |
| 单次 LLM 调用 | 输入已经充分，一次生成即可完成 | 无法在同一次模型调用中消费后来获得的工具结果 |
| 固定工作流    | 步骤及分支可以事先确定         | 新场景往往需要修改编排                       |
| Agent Loop    | 下一步取决于执行中的反馈       | 调用次数、成本和完成时间更不确定             |

Anthropic 对 workflow 和 agent 的区分也以控制路径为依据：前者由代码预设，后者由模型动态决定；其建议仍是先采用满足需求的简单方案，再用效果证明增加复杂度的价值。[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)

AaaS 以 Loop 为执行单位，是为了支持根据反馈决定下一步的任务。业务已有的确定性流程仍可保留。至于分类任务是否值得使用 Loop，还需要在同一模型、相同可用信息下比较质量、成本与延迟；前述实践观察尚不足以回答所有场景的选型问题。

## 3. 从一个 Assistant 场景理解 Harness

项目通常会使用 Agent SDK 实现 Loop，但 SDK 之外还有不少接线工作。Harness 这个词经常被用来指这些工作，却容易把业务内容和公共机制混在一起。

下面用一段虚构的工单处理对话说明这些职责，它不是已有产品的运行记录。

> **场景：整理并分配登录问题工单**
>
> _预设配置_：业务提供 system prompt，要求 Assistant 帮助处理当前用户可访问的工单，按团队规则给出分配建议，分配前取得授权，最终返回处理摘要和结构化结果。同时提供“工单分流”Skill、知识库检索与工单工具，并配置分配操作需要审批。
>
> **用户**：把今天还没分配的登录问题整理一下，分给合适的团队。
>
> **Assistant**：只处理企业客户，还是所有客户？
>
> **用户**：只处理企业客户。
>
> _执行过程_：Agent 读取“工单分流”Skill，查询符合条件的工单，再检索团队职责文档。文档提供判断依据，工单接口提供当前业务事实，Agent 据此提出候选分配。
>
> **Assistant**：这些工单建议分给身份认证团队。请确认以下工单和目标团队后执行。
>
> _审批与执行_：业务界面展示具体分配清单。用户批准后，执行服务核对批准对应的操作与参数，再调用分配工具。假设其中一条已被其他人领取，工具返回冲突；Agent 应说明该条未处理，或在授权范围内重新判断，不能仍将它列为分配成功。
>
> _返回结果_：Assistant 给出自然语言摘要和符合业务约定格式的处理结果，说明哪些已分配、哪些未处理，以及原因。
>
> **用户**：再看看昨天的。
>
> _下一轮_：业务将此前必要的对话和当前请求组织成下一次执行输入。

这个例子中的提问用来补充任务信息，审批用来授权具体操作。两者都可能等待用户，但只有审批会改变某次操作是否可以执行。自然语言里的“请先确认”也不能替代实际的权限检查。

这段过程用到了 system prompt、Skills、知识库检索、工具调用、澄清、审批和格式化输出。为了让 Loop 使用这些能力，系统需要提供上下文、绑定权限、把问题交给用户，再将回答送回对应的任务。

本文把这些围绕 Loop 的装配、约束和交接机制称为 Harness。这个定义帮助我们讨论职责，并不要求所有能力放进同一个包或同一个服务。

### 指令、Tools 与 Skills

当前设计把输入指令和 tools 视为 Agent Loop 的两个核心支柱。指令描述要完成的工作，tools 提供执行过程中可调用的能力。

在这个抽象下，Skill 本质上是一类特殊的文档或文件，不需要成为与指令、tools 并列的核心执行概念。调用方可以把少量技能正文放入上下文，也可以提供技能目录，让 Agent 经文档读取工具按需加载。Skill 中即使包含脚本或工具使用说明，也不会因此获得执行权限。

指令和 tools 描述了业务如何指导 Agent、允许它做什么。完整的执行请求还需要上下文、模型配置、输出要求和资源预算。这些配置决定 Agent 看见什么、使用什么模型、如何返回结果，以及最多消耗多少资源，应当由服务明确处理。

## 4. AaaS 与业务各自负责什么

建议由业务决定任务内容和业务规则，AaaS 提供执行这些要求的机制。

| 业务需要提供               | AaaS 需要承接                        |
| -------------------------- | ------------------------------------ |
| 任务目标、角色和业务规则   | 装配输入并执行 Loop                  |
| 本轮上下文与可访问的知识   | 消费上下文，调用受控读取能力         |
| 业务工具及其资源权限       | 绑定工具、检查执行范围、回传结果     |
| 哪些操作需要批准、谁能批准 | 在批准前暂停操作，接收决定并继续执行 |
| 对话界面与用户身份         | 输出执行事件、问题和结果             |
| 结果标准与成本要求         | 输出合同、运行预算、用量和审计       |

对话和上下文的长期存储由业务掌握。AaaS 可以缓存输入，也可以为了故障恢复短期保存执行快照；它不会因此成为业务会话的长期存储系统。

为了延续 Assistant 对话，业务在新任务开始时提供所需历史。任务中的澄清和审批继续原有工作，普通后续请求则开始新的工作。对话因此可以跨多次执行延续，无需让一个执行进程始终存活。

### Everything is tool

从 Agent 的视角看，查询工单、检索知识和提交分配，都可以通过 tools 使用。这让已有业务能力有机会被重新组合，而不必为每个任务预先规定全部步骤。

工具化并不改变权限归属。Skill 可以说明如何分配工单，真实工具仍要核对用户是否有权修改它；Agent 可以请求批准，批准是否有效仍由服务判断。模型看到一段指令，不等于它获得了其中描述的权限。

## 5. 完整的服务是什么形态

AaaS 的使用者需要提交任务、配置能力，也需要查看运行情况。这对应三类产品能力。

| 使用面   | 使用者要完成的事                                       |
| -------- | ------------------------------------------------------ |
| 业务接入 | 提交任务、观察进度、回答问题、批准操作、获取结果或取消 |
| 配置管理 | 提供工具与 Skills，配置模型凭证、访问范围和额度        |
| 运行管理 | 查看排队和执行情况，追踪费用，核对操作记录，处理异常   |

这三类能力可以由 API、SDK 和控制台共同提供；首版具体交付哪些界面由设计文档确定。

一次工作需要有稳定的身份，因此服务引入 Run。Loop 描述内部如何执行，Run 则让调用方能够查询、等待和管理同一次工作。业务提交后连接断开，可以查询原 Run；任务等待用户时，可以把回答送回原 Run。执行进程的生命周期不必与业务等待的时间相同。

业务应用把任务交给 AaaS，由它管理接纳、执行和结果交接，并调用模型供应商与业务工具。底层计算可以使用 FaaS，当前考虑 AWS Lambda。队列由谁维护、如何通知业务、怎样使用凭证和记录费用，则需要在服务接口和运行规则中说明。

## 6. 业务如何接入

业务可以先接入一个具体任务：定义指令和结果格式，提供所需上下文、工具、Skills 与模型配置，然后创建 Run。执行期间，业务接收进度和交互请求；结束后，获取结果并更新自己的业务状态。

对于摘要任务，可能提交输入后等待结果就足够了。对于 Assistant，还需要展示问题和审批内容，认证用户的回复，并保存下一轮所需的对话。两者使用相同的执行能力，但不必拥有相同的产品界面。

服务还应让调用方看清一次工作的消耗和过程：使用了什么模型、调用了哪些工具、哪些操作获批、哪些已经成功，以及费用归属于哪里。模型凭证可以由平台或调用方提供。

接入完成后，业务仍然拥有自己的用户、数据和成功标准，并根据实际任务质量判断 Agent 是否值得采用。
