如果要让一群 Agent 一起工作，最先应该设计的到底是什么？

一种自然的设想是建立 Agent 人才市场、公司和培训机构。人才市场负责提供不同性格和工作风格的 Agent，公司从中招募员工，培训机构根据任务训练出更合适的 Agent。这里的“训练”不一定是改变模型参数，更多时候是构造 prompt、skills、tools 和工作方式，让一个可重复的角色逐渐变得可靠。

这个想法听起来像是在构造一套 Agent 社会。但进一步分析会发现，“社会”并不是从很多个体开始的。真正困难的地方是：信息如何在这些个体之间流动？谁应该在什么时候看到什么？一个角色为什么要把结果交给另一个角色，而不是继续自己处理，或者退回去重新询问？

如果这些问题没有答案，所谓公司就只是若干个 prompt 的集合。角色越多，混乱越快发生。

因此，本文不先定义一家公司有哪些部门，也不从一张完整的 DAG 出发，而是从不同领域的系统中提取结构，推导一种更小、更松、更适合 Agent 的组织机制。最终得到的 WorkCell，也许不是一套完整的工作流引擎，而更像一张异步的信息加工网络。

## 先放下线性的工作流

开发一个功能，最容易画出的流程是：需求分析、设计、开发、测试、发布。它适合放进介绍文档里，却不太像真实工作。

真实的过程可能是：需求角色发现两个约束互相矛盾，于是回去追问；设计角色发现现有架构根本承受不了这个需求，又回到设计之前；开发拆出三个相互独立的任务，其中一个任务需要等待外部资料；测试发现的问题，有些应该退回开发，有些其实说明需求本身不完整。中途还可能有人加入，修改问题的优先级，或者直接决定不做了。

这不是一个方向明确的管道，而是一个会回流、分叉、等待和中断的信息系统。

线性的工作流当然有用。对于边界清楚、变化很少的任务，它简单、容易检查，也容易向别人解释。问题在于把它当成所有组织的底层模型：一旦真实任务需要回流和临时协作，原本清楚的线就会变成越来越多的条件分支。

从“工作流节点和连线”出发设计这类系统，很快会遇到几个问题。复杂流程很难描述；一个角色可能需要多个实例；两个不同来源的消息可能必须同时到达；某个角色完成工作以后，下一步不一定由预先指定的角色接手，而是要根据结果来决定。为了覆盖这些情况，工作流定义会不断增加条件、状态和特殊语法，最后变成只有设计者自己看得懂的程序。

这和 Agent 的目标有些冲突。组织设计者希望 Agent 能读懂组织规则，并且能提出修改。如果规则本身已经接近另一种编程语言，修改它就必须先理解这门语言的全部运行时语义，组织就失去了可塑性。

因此，问题可以换一种问法：能不能只描述角色、消息和消息进入角色的方式，让 Agent 自己根据工作结果决定下一站？

## 几个领域给出的暗示

这不是把别人的概念机械搬过来。区块链、信息论、工程控制论、集成电路和网络工程解决的问题不同，但它们都在处理一个相似的事实：系统由许多相对独立的部分组成，部分之间不能共享全部状态，只能通过有限的信号协作。

### 区块链：把一次处理看成一笔可追溯的交易

区块链最值得借鉴的，不是共识、挖矿或者代币，而是它对“发生过什么”的执着。

一条消息进入系统以后，不能只停留在某个 Agent 的内存里。它应该有稳定的身份、来源、类型和版本；一次处理应该能够留下接收、执行、输出和确认的记录；一个输出发往哪里，应该像交易发往一个地址一样清楚。这样，当系统出现错误时，至少应能回答：哪条消息触发了哪次处理，使用了哪个版本的角色，生成了哪些后续消息。

这并不意味着要把 Agent 放到链上。模型调用有随机性，工具会修改文件，执行时间也不可预测，让它们成为链上智能合约并不合适。更实际的做法是，把一次 Agent 调用看成一笔内部交易：运行时原子地认领输入，持有任务租约，保存输出，确认输入已经被处理，并生成一张 receipt。

消息本身可以是不可变的。修正不是修改历史消息，而是产生一条新的消息，引用原来的消息。角色定义和消息协议也应该有版本，某次运行一旦开始，就固定它们的版本。这样既保留了实验性，也避免同一条消息在运行期间悄悄改变含义。

### 信息论：传递的不是全部事实，而是足够行动的信息

Agent 之间不可能传递整个上下文。一个研究角色读了很多材料，最后交给设计角色的，通常只是结论、约束、证据位置和仍然存在的不确定性。问题在于，摘要不是中性的压缩。被省略的例外，可能正是下一个角色做决策所需要的内容。

因此，消息不应该只有一句“应该这样做”。它至少要同时保留两种信息：一份让下游快速行动的紧凑摘要，以及可以回到原始事实的来源、文件路径、版本或上下文拉取方式。前者降低沟通成本，后者给被压缩的信息留下恢复路径。

这也解释了为什么“让 Agent 自己找上下文”不能成为万能方案。如果消息里没有留下来源，或者来源已经失效，拉取机制只能把不完整的摘要再读一遍。信息是否充分，也不适合被一个统一的 `informationScore` 量化。是否充分取决于接收者接下来要做什么，应该由角色的工作判断，或者由另一个审校角色来判断。

消息管道还是有限容量的信道。并发数、队列长度、模型成本和工具资源都会造成背压。一个管道不是“只要发过去就一定会处理”的黑洞；发送被接受，应该意味着消息已经持久化，而不是意味着工作已经完成。满载、等待、重试和死信都应当可观察。

### 工程控制论：组织不是流程图，而是反馈系统

从工程控制论看，WorkCell 更像一个异步的离散事件控制网络。

真实世界和工作区是被控制的对象，Role 是控制器，消息是测量结果或控制信号，工具是作用于外部世界的执行机构，Pipe 是局部回路中的队列和运行条件。人类、评估器和组织管理者处在更外层，负责观察系统是否偏离目标，并且调整角色和规则。

这个视角带来一个很重要的提醒：反馈不是异常，也不是流程失败。设计者发现需求矛盾，测试者把问题退回开发者，研究者指出证据不足，这些都是系统正常运行的负反馈。一个允许回流的系统，反而比一个试图把所有路径提前写完的系统更接近真实组织。

但反馈回路也会振荡。两个角色互相把消息退回去，或者同一件事在不同管道之间来回转发，系统就会进入正反馈。解决办法不是强迫所有流程变成单向，而是给运行时增加边界：最大跳数、超时、成本预算、重试次数、版本标记和可观察的原因。角色仍然可以自由判断，但判断不能让系统无限消耗资源。

角色的迭代也应该是一个更慢的外层回路。一次运行中的角色版本应该保持不变，运行记录交给评估器和培训者，培训者提出新的 instruction、skills 或 tools，再用新的任务验证，最后才激活新版本。否则，系统会一边执行一边修改自己的控制器，出了问题很难知道究竟是任务变了，还是角色变了。

### 集成电路：异步 FIFO 和“同时到达”的问题

集成电路设计提供了另一个很具体的类比。一个 Role 像处理单元，一个 Pipe 像异步 FIFO，Message 是在接口上传输的事务，多个并发实例像流水线中的多个处理通道。系统不依赖一个全局时钟，每个部分在有输入、有能力处理时自行推进。

这正好对应 Agent 的执行特点：不同 provider 的响应时间不同，工具调用可能很慢，人类消息更无法按固定周期到达。运行时要处理的重点不是让所有角色同时行动，而是正确地持久化消息、分配租约、续租和回收执行权，并且在同一条消息被重复投递时避免产生无限副作用。

集成电路里还有一个和 Agent 组织非常相似的问题：一个处理单元需要等待多个输入。比如发布前既要有实现结果，也要有安全审查结果。简单地说“两个消息都到了就执行”还不够，因为必须知道它们是否属于同一个任务。这里需要一个关联键，运行时按键建立一张小型的等待表（scoreboard），只有每个输入槽都收到一条匹配消息时，才原子地组成一次调用。

这可能是整个设计里唯一无法完全隐藏的复杂性。但它应该保持局部：只在确实需要多个输入的 Pipe 上声明命名输入槽，而不是给所有消息都增加一套工作流状态。至于“最近的一条审查结果”“持续合并所有更新”这类语义，不放进核心。需要这些语义时，可以让一个专门的汇总角色显式地产生一条当前状态消息，或者让角色通过上下文拉取。

### 网络工程：Agent 选择逻辑地址，运行时选择实例

网络工程让“角色”和“实例”之间的关系变得清楚起来。

Agent 不应该知道某个开发者实例运行在哪台机器、哪个进程，更不应该直接调用 worker 地址。它只需要发现一个自己有能力发送到、并且接收目标消息类型的逻辑 Pipe。运行时再负责从这个 Pipe 的并发池里选择一个可用实例。

因此，Pipe 同时具有几种网络属性：它是一个逻辑服务端点，是一个队列，是角色的绑定，也是角色在本地执行时所处的工作条件。消息定义像应用层协议，消息 envelope 里则放置传输所需的身份、关联键、版本和追踪信息。`listPipes` 是受限的服务发现，`send` 是持久化后的异步投递，租约则是消费者对一条消息的临时所有权。

这里需要区分数据平面和控制平面。普通角色只能看到自己任务范围内可用的消息类型和 Pipe，不能随意修改角色定义、并发上限或组织结构。管理者和培训者处在控制平面，才可以发布新版本、调整资源、观察事件和激活候选角色。这样既保留了 Agent 根据结果选择下一站的自由，也不会让一次业务处理拥有修改整个组织的权限。

## WorkCell 的最小模型

把这些启发合在一起，WorkCell 可以被定义成一种“带有角色的异步消息处理网络”，而不是工作流图。

它的核心只有三种作者需要理解的实体：

```text
Role
  instruction + skills + tools

MessageDefinition
  name/version + JSON Schema

Pipe
  input + role + work + concurrency
```

Role 描述一个可重复的工作方式。它不是一个拥有长期记忆的数字员工，也不是一个需要自己规划人生的个体。它更接近一块可以反复装配的处理逻辑：给它相同的指令、技能、工具和输入，它应该在可接受的范围内表现出相同的倾向。

MessageDefinition 只描述消息的形状。它不描述消息应该发给谁，也不承担任务完成、结果合并或者业务正确性的判断。文件路径、引用关系和外部上下文入口都可以作为消息字段出现，不需要额外造一个叫 Artifact 的核心实体。

Pipe 把输入消息、Role、并发数和一小段局部工作说明放在一起。相同的 Role 可以绑定到多个 Pipe，因为它在不同入口处可能做不同的工作。Pipe 也可以有多个命名输入槽，用于表达必须同时具备的消息。

同一个 MessageDefinition 可以被多个 Pipe 接收。消息定义只回答“长什么样”，Pipe 的 `input` 才回答“哪个入口愿意接收它”。这使得消息协议可以复用，而组织关系仍然保持在局部。一个 Agent 如果需要通知多个角色，就显式地向多个 Pipe 发送；运行时不默认广播，也不替它猜测应该通知谁。

例如，一个很小的系统可以这样写：

```yaml
messages:
  - name: requirements.ready
    version: 1
    schema: ./schemas/requirements-ready.json
  - name: design.ready
    version: 1
    schema: ./schemas/design-ready.json

roles:
  - name: designer
    instruction: ./roles/designer.md
    skills: [research, architecture]
    tools: [workspace]

pipes:
  - name: design.in
    input: requirements.ready
    role: designer
    work: 为需求形成可验证的设计，并处理发现的矛盾
    concurrency: 2
```

这个定义故意没有 `next`、`to` 或 `outputs`。Pipe 不决定处理完成后要连到哪里。它只决定什么消息可以进入、由什么角色处理，以及最多同时处理多少条。Agent 在完成工作以后，可以通过受限的服务发现看到候选 Pipe，然后根据自己的输出选择下一站：

```text
listPipes({ accepts: "design.ready.v1" })
send("implementation.in", "design.ready.v1", body)
```

这里的自由不是无限的。运行时会检查目标 Pipe 是否存在、是否接受这个消息版本、消息是否符合 schema、调用者是否具有发送能力，以及队列是否能够接收。运行时不判断设计是否真的好，也不通过关键词或正则表达式猜测 Agent 的意图。结构上的问题由协议检查，语义上的问题交给角色和评估器。

## 一个真实任务如何流动

以开发一个功能为例，入口可能是一条 `feature.request` 消息。它被送入需求 Pipe，需求角色输出 `requirements.ready`。设计角色收到以后，可能输出 `design.ready`，也可能输出 `requirements.conflict`，把问题重新送回需求入口。

当设计足够清楚时，设计角色可以产生三条 `implementation.task` 消息。它们拥有同一个关联键，但不需要由一个中央协调器合并。开发 Pipe 有三个并发槽，三个 Role 实例分别处理它们。某个开发者完成以后，把 `patch.ready` 发给审查 Pipe；审查者可以输出 `review.passed`，也可以输出 `rework.request`，重新进入开发 Pipe。

发布 Pipe 如果要求实现和审查同时存在，可以声明两个输入槽：

```yaml
pipes:
  - name: release.in
    inputs:
      implementation: patch.ready
      review: review.passed
    role: releaser
    work: 只有同一关联键的实现和审查都到达时才准备发布
    concurrency: 1
```

运行时按照关联键等待两种消息，并且原子地消费这一对输入。没有“先到的消息触发一次，再等另一条消息”的隐含行为，也没有要求发布角色了解队列的内部实现。它看到的是一个输入 bundle。

这个流程没有全局的“完成”状态。某个输出如果是人类需要的结果，人类就订阅或等待相应出口；如果还需要下一步，就由角色继续投递。一个开发任务可以在某个出口暂时停住，也可以重新进入需求回路。WorkCell 负责可靠地加工消息，不负责替业务宣布一切已经结束。

## 运行时应该保证什么

作者看到的模型很小，背后仍然需要一个可靠的运行时。它至少要负责消息持久化、投递记录、队列、并发、租约、确认、重试、死信、原子 join、背压、事件和防止旧执行者覆盖新结果的 fencing。

发送被接受，表示消息已经持久化；默认语义是至少一次投递，而不是昂贵又难以保证的 exactly-once。工具有副作用的 Role 需要通过幂等键、事务边界或者工具本身的去重机制来保护。重试只解决传输或执行失败，不等于语义质量变好了；语义上的冗余应该由独立审查者、不同角色或人工反馈提供。

Harness 则是执行一轮 Role 所需要的血肉：它提供 prompt、skills、tools、workspace、provider/model adapter、secret 引用、事件流、steer 和 cancel。上下文属于调用方或显式的上下文服务，可以作为参数传入，也可以由 Role 按约定拉取。WorkCell 不应该偷偷为每个消息创建一份不可见的长期记忆，否则消息网络又会退化成一堆互相无法观察的个体 Agent。

第一版可以只在本机运行。底层用 SQLite WAL 保存队列和事件，WorkCell 把一个输入 bundle 映射成一次 Run。以后再替换 runner、provider 或 sandbox，而不改变消息层的概念。sandbox 也应当是执行能力的边界，不是消息协议的一部分；普通函数和 Agent loop 都可能需要它，只是风险和资源策略不同。

## Agent 公司其实是一个更慢的系统

到这里，“Agent 人才市场”和“培训机构”有了比较明确的位置。

人才市场提供经过版本化的 Role。公司或模块定义需要哪些 Pipe、哪些消息协议、哪些资源限制，并且可以在自己的控制平面里招募和替换 Role。培训机构观察运行事件、失败原因、人工反馈和评估结果，提出新的 instruction、skills、tools 或 provider 组合。优秀的候选版本经过测试以后，替代旧版本。

这不是某个个体 Agent 的成长故事。迭代对象是一个可复用的角色和它所在的组织结构，关注的是一批任务上是否变得更可靠、更省成本、更能处理边界情况。一个角色的经验不会自动变成它的私有记忆，而是通过可审查的定义变更回到控制平面。

从控制论的角度看，业务消息是快回路，角色训练和组织重构是慢回路。把两者分开，才能知道一次任务失败是偶然的执行问题，还是角色定义需要改变。未来甚至可以让负责人 Agent 参与培训和组织设计，但它提交的仍然应该是候选定义、评估证据和变更理由，而不是直接修改正在运行的系统。

## 仍然保留的疑问

这个设计并没有解决所有问题。它只是把必须解决的问题放到了比较合适的地方。

首先，Agent 如何发现候选 Pipe 仍然需要更细的权限和命名空间设计。全局广播会造成消息爆炸，完全隐藏拓扑又会让 Agent 无法行动。比较实际的方向是只提供带作用域的发现结果：当前任务、当前组织、当前角色能看到哪些可以发送的 Pipe，而不是把整张网络交给它。

其次，多输入 join 的关联键怎么产生、如何传播、什么时候过期，需要真实任务继续验证。现在的“一条消息对应一个槽、同一 key 原子组合”是一个有意保守的起点。它比 `latest`、`combineLatest` 一类隐含状态更容易解释，但也可能不适合所有研究型工作。

再其次，资源治理不能只看并发数。模型费用、工具危险等级、文件系统范围、等待人类的时间，都会成为系统的实际容量。管道的 `concurrency` 只是一个局部旋钮，真正的背压需要运行时同时观察队列、租约、成本和 sandbox 资源。

最后，角色的“质量”不能从消息是否符合 schema 推断出来。schema 只能保证形状正确，不能保证内容有用。质量需要通过任务结果、独立审校、用户反馈和长期统计来判断。这个边界必须保留，否则结构化协议很容易被误解成自动正确性。

## 没有总指挥，也可以形成秩序

经过上述分析，WorkCell 与最初设想中的 Agent 公司已经是两种不同的抽象。

它不是先建立一个庞大的组织，再给每个部门写一张总流程图。它更像一组可以插拔的异步处理单元：Role 提供稳定的工作倾向，Message 提供可验证的形状，Pipe 提供局部的入口、工作条件和容量。Agent 读到输入以后，根据结果发现下一条可行的信息路径；运行时负责让这条路径可靠地发生，并且把每一次处理留下记录。

区块链提供了不可变消息和处理收据的思路；信息论说明了为什么要给摘要留下回到事实的路径；控制论提示系统把回流当作反馈，并给反馈回路设置稳定性边界；集成电路揭示了异步队列、并发和多输入同步的工程问题；网络工程则说明 Agent 应该寻找逻辑服务，而不是操纵具体实例。

这些启发最后都指向同一件事：Agent 组织的核心不是把更多智能塞进一个总调度器，而是让信息流动得足够清楚，让每一次加工都可观察，让错误能够回流，让资源消耗有边界，让角色可以被替换。

如果这个方向成立，那么一个“公司”不必首先拥有完整的层级和流程。它可以从一个入口 Pipe、几个消息定义和一个角色开始，在真实任务中逐渐长出反馈回路。组织不是一次设计完成的建筑，而是许多次可追溯的信息处理累积出来的结构。
