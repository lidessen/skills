# Defrag change and verify

用户要求实际整理时使用这份参考。它约束修改的完整性，不规定固定命令或固定测试数量。

## 修改前

- 检查 `git status --short` 和相关 `git diff`，识别并保留他人的未完成改动。
- 先确认对象身份、消费者、权威来源、公开契约和失败处理；不因为删除方便而改变它们。
- 选择一个能暴露错误整理的行为基线。无法取得基线时记录限制，不假装完成。

## 修改时

- 优先合并重复规则、修正归属、补齐引用和入口；只有负担确实降低时才移动或拆分文件。
- 同一语义变化一起修正调用方、构建配置、测试、文档链接和注册入口。
- 已确认失效的内容才删除；仍有决策价值的历史依据退出当前指导入口但保留可回查位置。
- 不把可疑对象全部移入 archive 来制造“完成”，不新建第二份权威文档或永久台账。
- 用户授权范围内直接推进；发现新产品需求、更大设计争议或不可逆风险时记录并收窄本轮。

## 修改后

1. 沿修改前的问题重新定位入口、规则、例外和依据；确认维护责任没有变得更分散。
2. 做一次有边界的关系回看：确认合并后谁维护规则、其他消费者是否仍保有需要的区别、
   仍有效的迁移计划是否被错误宣布结束。只扩展到能改变当前判断的关系，不建立全仓图。
3. 运行与语义变化相称的定向检查。优先验证能暴露错误删除、错误路由、链接断裂、构建
   入口丢失和运行时行为回归的检查。
4. 选择一个原本容易误判的真实问题，检查整理后能否从入口找到负责位置、规则与依据，
   并完成原来的判断。没有前后对照时只报告这次观察，不宣称理解成本已被证明降低。
5. 区分格式/类型/测试通过、运行时观察和用户验收；未验证内容保留为未知。
6. 最后再次检查 `git status --short` 和相关差异，交付修改、保留理由、验证结果和未决项。
