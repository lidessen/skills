# AI 味的表达痕迹与诊断

SKILL.md 讲了模型默认写成难读文档的四个原因：不感到读者成本、缺材料、输出预算、语域习惯。
这份文件列的是这些原因留在文本上的痕迹，按可定位的位置分四组：词汇与标点、句法与节奏、
篇章结构、内容。每组写它长什么样、通常在替什么东西占位、怎么改。词表来自
维基百科编辑的观察和几份带频率统计的中文对照研究（见文末来源），不是主观印象；但单个
命中不是证据，多个叠加才是。文末的“不能当判据”表是硬约束，命中那些直接放行。

## 一、词汇与标点

这一层最容易识别，也最容易只改这一层就以为改好了。改完这层必须继续往下看。

### 英文高频词

维基百科 AI 清理小组按模型时期统计的词，出现一两个是巧合，一段里出现多个是最强的单项信号：

| 类别   | 词                                                                                                                                                                                                   |
| ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 动词   | delve, underscore（比喻义）, highlight / showcase / emphasize（作“说明、体现”）, foster, bolster, garner, leverage, streamline, enhance, ensure（非技术保证义）, navigate（比喻义）, boast（作 has） |
| 形容词 | crucial, pivotal, key（作形容词）, robust, seamless, comprehensive, intricate, meticulous, vibrant, enduring, valuable, nuanced, holistic                                                            |
| 名词   | landscape / tapestry（抽象义）, testament, interplay, realm, journey（比喻义）, synergy                                                                                                              |
| 句首   | Additionally, Moreover, Furthermore, Notably, Importantly, It's worth noting that, It is important to                                                                                                |
| 收尾   | In summary, In conclusion, Overall, Ultimately, Happy coding!, Feel free to…                                                                                                                         |

改法：空泛的动词换回 is / has / does 和具体动作；形容词有事实依据时换成数字或行为；句首连接词在
上下文能自行衔接时可删；收尾句若只剩礼貌套话可删，帮助回顾重点或明确下一步的内容保留。

| 过渡填充   | 综上所述、总而言之、总的来说、由此可见、不难看出、换句话说、简而言之、归根结底、本质上、核心在于、关键在于、一句话总结                 |

| 商业黑话   | 赋能、助力、打造、抓手、闭环、颗粒度、对齐、拉齐、沉淀、痛点、降本增效、底层逻辑、顶层设计、链路、触达、拉通、洞察、赛道、卡点、一站式 |

改法同上。“进行 + 动词”“实现了对……的支持”这类形式动词改成动词本身。

### 标点与排版

- **破折号。** 英文 em dash 和中文“——”都被模型当万能标点，用在人类会用逗号、括号、冒号、
  句号的位置，尤其是“不是 X——而是 Y”的转折。人类维护者文档里破折号很少（英文 22 篇样本
  16 篇为零）。检查它是否表达插入、解释或转折；关系不清时再换标点或重写，不按出现次数删。
- **提示性冒号。** 两种：“核心是：”“关键在于：”“一句话总结：”后面接结论；一行以冒号结尾接列表，
  删掉这行信息不减。中文对照统计里后者是倍率最高的单项（AI 是人类的 9.4 倍），前者 3.8 倍。
  直接说结论；只为宣布列表存在的那一行删掉。句中总说分说的冒号是规范用法，不动。
- **加粗。** 每条列表加粗小标题、正文里每个“关键词”都加粗、“**注意**：”。人类文档加粗留给
  警告和少数术语首现。
- **标题 Title Case。** 英文小节标题每个实词大写（“Getting Started With The API”）。GitHub
  和多数项目文档用 sentence case。
- **每个标题前一条分隔线**、**跳级标题**（`#` 直接到 `###`）、**弯引号与直引号混用**、
  **emoji 当项目符号**。这些是聊天界面 Markdown 的残留。
- **中文全角半角混用不一致。** 同一篇里“（）”和“()”、“，”和“,”混着用。跟随项目惯例统一。

## 二、句法与节奏

### 否定式对比（“不是 X，而是 Y” / “not just X, but Y”）

先立一个读者并没有的误解再推翻它，或者用“不仅……更是……”把一件事说成两层。中文对照研究
把它叫“翻案腔”“洞见感骨架”，实测 AI 是人类的 3.4 倍，五家模型都有。人类写作也用，
但 X 通常是真实存在的常见误解。

改法：没有需要澄清的误解时，直接从正面说 Y；X 确实是读者可能有的想法时，保留对比帮助
辨别。是否保留取决于这处对比的作用，不给全文设次数上限。

### 三件套

“adjective, adjective, adjective”“短语、短语和短语”，三条列表、三个例子、三个理由。
模型用它让浅分析显得完整。人类文档的条目数随事实：有两条写两条，七条写七条。

改法：数一数每个并列结构，问第三项是不是凑的；是就删。

### 相邻句同构

连续几句逗号数相同、成分顺序相同、长度接近；或者每段都是“[陈述], [连词] [第二陈述]”。
单看每句都通，连着读像节拍器。中文对照统计里相邻句同构是 AI 的两倍。

改法：让句子结构跟着内容走，解释因果用长句，下判断用短句，列参数用列表。刻意长短交替
会制造另一种节拍，不用。

### 分词尾巴与浅分析（英文）

“…, highlighting the importance of X”“…, ensuring a seamless experience”“…, contributing to
the broader ecosystem”。句末挂一个 -ing 短语给前面的事实补一句意义。维基百科编辑称之为
superficial analysis。删掉尾巴，事实自己会说话。

### 避开 is / are

“serves as”“stands as”“represents”“marks”“features”“offers”“refers to” 替代 is 和 has。
维基百科指南引用的一项研究测得 2023 年学术写作里 is/are 用量下降超过 10%，此前多年没有
大的变化。写 “X is a …”“X has …”。

### 段首零主语评论、“这意味着”式复述

段落以“更重要的是”“从更深层次看”“这意味着……”“This means that…”开头，后面是对上一段的
同义复述。先看它是否在唤回前文、强调轻重或衔接下一步；没有新信息不等于没有作用。
只有当前上下文不需要这层衔接、复述反而打断阅读时，才删改。

### 电报体压缩

系统提示要求“简洁”“少输出”时，模型会省掉功能词、用符号代替句子；用户还观察到长文写到
后半更明显（未做过试验）。它和上面几条不同：来源是输出预算，和内容多少无关，所以事实齐全
的文档也会有。

最先出现的位置是写作者自己觉得“本来就该短”的地方：规则、标题、列表条目。写规则时滑向
格言体（“一句只推进一件事”：省了“话”，“推进”是比喻，“一件事”没说清什么算一件），写标题时
滑向冒号标签加对比（“定位：翻译，不是去味”：冒号标签、“不是 X”、当场造的缩略“去味”），
写条目时滑向单句提纲。这三个例子都出自本 skill 自己的早期版本，写进清单的同一天又用上了，
所以清单只能事后逐条对照，不能指望它改变生成。

- 篇章级，最常见：整篇写成提纲。三层编号小节（1.1、2.3），每个事实一条单句条目，被否方案
  排成表格，全文没有一段把机制和后果连起来说的话。试验里加一句“回复务必精简”，同一份事实
  清单从 7 个标题、3 条列表变成 16 个标题、21 条列表、12 处加粗。设计文档读者要的是推理过程，
  提纲只给结论。
- 中文：连着省主语，读者要猜“它”指谁（“取不到令牌重新入队，延迟上限 30s，熔断后不发”）；
  箭头、等号、斜杠、冒号标签代替句子（“配置错 → 启动失败”“延迟 = 桶恢复时间”“读/写路径”
  “结论：可行。风险：Redis 单点。”）；自造缩略（“限速配”“主从切”）；动词压成名词堆
  （“完成限速配置校验前置”）；半文言连用（“若无则跳过，有则覆盖，均需重启”）。
- 英文：丢冠词和 that / which（“Config lives in file. Worker reads queue, applies limit.”）；
  名词堆（“per-domain token bucket rate limit config page”）；缩略（w/, b/c, cfg, impl, req/resp,
  opt.）；分号和括号把三句压成一句；“Note: / Tradeoff: / Result:” 标签句连排。

读者的感受是在看笔记。人类维护者也写片段，但写在模板槽位（“None.”）、列表条目、表格和命令
说明里；正文段落是完整句子。改法：需要解释关系的提纲改回段落，补读者缺少的后果、主语、动词
和连词。读者不熟悉的缩略语补全称；符号或标签让关系不清时换成陈述，熟悉且准确的术语和记号保留。改完可能变长，
篇幅是否合适仍取决于任务。长度受限时先删无助于阅读的填充和次要展开，保留有用的复述、必要事实、条件和用户要求；
无法兼顾时说明范围或分层展开，不静默漏写。长文也检查后半是否出现了指代和条件缺失。

### 过长前置定语（中文）

中心名词前的修饰让读者难以判断对象或条件时，调整语序或拆句。字数和“的”的数量只能提示
回读，不能单独判定长句有问题。

### 翻译腔（两个方向）

用英文的习惯写中文：每句带主语和代词回指、显式的“因为……所以”“当……时”、冠词式的“一个”、
名词化的“进行”“实现对……的支持”。用中文的习惯写英文：逗号串起的长句不断开、冠词和单复数
缺失、“carry out”“realize”“relatively”“a certain”“at present”这类逐字对译。过度翻译：把
issue、token、Pull Request 翻成“议题”“令牌”“拉取请求”，把 `--dry-run` 翻成“干跑”，把
“under the hood”翻成“引擎盖下”。新写的文档也会有，翻译任务里更集中。症状清单、语料计数和
改法见 [language-notes.md](language-notes.md)。

### 拟人化喻体与抒情词

“像一位经验丰富的管家”，以及给抽象概念配的感官动词（安放、抵达、微光、滚烫）。技术文档里
几乎不出现。删。

## 三、篇章结构

### 总分总与模板节

开头总述 → 分点展开（每点等长）→ 结尾重复开头。README 则是 Overview / Features / Installation /
Usage / Contributing / License / Roadmap 一字不落，每节都填满。人类 README 的节随项目真实状态；
esbuild 只有 “Why?” 一节。

改法：没有事实也没有阅读作用的模板节删掉；篇幅随解释需要安排。结尾可以回顾重要内容，
不要为了凑齐总分总而重复，也不要为了去模板而删掉有用的回顾。

### 密度均匀、层次不降

每句都是一条新事实，段与段等长，没有一句在把上一句往具体处降。文档很短、很齐，读者要
自己补例子和后果。这是模型文档里最难察觉的一种，因为单看每句都对，也没有任何词表能命中。

量出来的差别（去掉代码块和表格）：人类中文说明文档每千字有 0.6 到 2.7 处“比如 / 例如 /
也就是说 / 假设”这类举例标记，英文每千词 1.7 到 5.2 处 “for example / such as / that is /
suppose”；模型产物普遍为 0。人类中文句均 23 到 57 个汉字，模型产物 16 到 25；“的”在人类
说明文档里占汉字的 3% 到 6%，模型产物 2% 到 3.5%。这些数字来自本 skill 的语料和试验，
样本不大，作校准用，不作阈值。

改法：检查读者理解或行动时还缺哪一步，再补对应的解释。后果、场景和例子是可选的解释方式，
不必每段依次写全；是否复述还要看读者是否需要回忆上下文、感知轻重或记住行动。例子只能来自已有事实。“也就是说”
“比如”“所以”是否有用，要看它们后面的内容有没有帮助理解。

### 段末总结、节首预告

“总之……”“In summary…”“本节将介绍……”“In this section, we will…”只是形式线索。
检查后面的内容是否帮助读者回顾重点、恢复上下文、决定是否继续读或记住下一步；有这些作用
就保留，不按词头或所在位置直接删。

### 加粗段首小标题连排

“**Format.** …”“**Migration.** …”是加粗小标题列表的段落版。读者要跳读的独立主题可以这样标；
同一条论证里的几段不需要，人类更常写成主张式小节或直接连成段。

### “挑战与展望”节

“尽管面临挑战……但仍然……”“未来，X 有望……”。这是维基百科 AI 清理列出的固定骨架，技术文档里
对应“路线图”“未来计划”里没有日期、没有 issue 的愿景条目。没有决定的事写“未决定”，没计划的
不写。

### 面面俱到的对称覆盖

每种方案、每个选项各一段、篇幅相同、不说推荐哪个。缺的是立场。写出默认路径，其他路径只说
什么时候需要它。

### 序数词小标题、每段一个编号

“一、二、三”或“1. 2. 3.”连续三个以上当小标题，或每段以“首先/其次/最后”开头。正文里偶尔用
“首先……其次”与人类无差别；通篇编号才是。

## 四、内容层

这一层是 AI 味的根，也是表达层痕迹反复长回来的原因。

下面的补写建议用于新写内容。修订已有文档时，未核实的原有主张按主文的保留原则处理，
另列待确认项；找不到证据不等于确认“未测”或“暂无”，也不授权删除或弱化作者的承诺。

- **编造。** 没测过的基准、没定的时间表、模板带出来的“跨平台支持”、“经过大量生产环境验证”。
  必须回到来源逐条核对；无依据的内容不新增，只有来源确认未测或暂无时才这样写。
- **形容词代替数字。** “高性能”“显著提升”“extremely fast”。有测量写数字和条件，缺少测量依据时不新增性能结论。
- **泛泛的保守话。** “可能需要根据实际情况调整”“results may vary”。写出是哪个参数、现在什么值、
  为什么不确定、之后靠什么决定：“默认 30 秒没有测过，是按经验定的；上线后超时告警多再调大”。
- **对读者的假想。** “无论你是初学者还是专家”“Whether you're…”。写出这份文档实际面向谁。
- **把未知写成已知。** 来源说“一个用户报告能用，未测”，文档写成“支持”。按来源的确定程度写。
- **无源引用。** “研究表明”“experts say”后面没有链接。查找来源；无法核实时，新稿不引入，已有文稿另列待确认项。
- **意义拔高。** “具有里程碑式的意义”“marks a pivotal moment”“stands as a testament to”。
  技术文档不需要评价自己的重要性。

## 不能当判据的特征

这些看起来像 AI，但对照统计或人类文档样本显示人类同样用，甚至用得更多。命中这些不改；
为了“更像人”去改它们，会制造新的 AI 味。

| 特征                                 | 为什么放行                                                                   |
| ------------------------------------ | ---------------------------------------------------------------------------- |
| 句长、段长不够参差                   | 中文对照实测 AI 与人类无差别；刻意制造长短交替是在造新腔调                   |
| “X 是一个……” / “X is a…” 开头        | 中英文人类 README 最常见的开头，第二句给具体事实即可                         |
| 正文里的“首先……其次”                 | 与人类无差别，只管小标题通篇编号                                             |
| 句内同构排比（“提升效率，降低成本”） | 人类用得不比 AI 少，只处理句间连续同构                                       |
| 问句、问句小标题                     | 人类正文问句是 AI 的十几倍；“Why shouldn't I use ripgrep?” 是人类写法        |
| 名词化、长句、书面被动               | 现代中文书面语的正常写法；TiDB、RocketMQ 文档的长句都是人写的                |
| 单个破折号、单个 however、弯引号     | 单独出现证明不了任何事，叠加才算                                             |
| 反复写全称、少用代词                 | 人类技术文档比 AI 更常重复同一术语；同义词轮换才是 AI 味                     |
| 重复起句的修辞                       | “她来了。她看见了。她征服了。”是有意为之                                     |
| 真实的免责声明、范围说明、安全提示   | 保留                                                                         |
| 模板槽位、列表、表格里的片段         | “None.”“未测”“默认 8”是人类写法；只处理正文段落里的电报体                    |
| 举例、说后果、复述、小结             | 可以帮助理解、唤回上下文、加深印象和强调轻重；没有新事实不能单独成为删除理由 |
| 工整的语法与一致的风格               | 工整不等于 AI；很多作者是专业的或被编辑过                                    |
| 项目已有的排版惯例                   | antd、Vant 的 emoji 特性列表是社区习惯，跟随项目                             |

优先级：误杀防护高于所有词表。词表里的词在当前句子里承担实义时放行（“underscore” 指下划线字符，
“收敛”指算法收敛，“闭环”指控制闭环）。

## 使用方式

写完初稿后按层过一遍，从第四层往上：先核事实，再看结构，再看句式，最后扫词表和标点。
顺序反过来会出现只换了词的假修好。修别人的文档时先锁保护清单（命令、参数名、数值、URL、
引用原文），再动表达。

## 来源

- [Wikipedia:Signs of AI writing](https://en.wikipedia.org/wiki/Wikipedia:Signs_of_AI_writing)：维基百科 AI 清理小组的现场指南，含按模型时期统计的英文词表和大量真实例句。
- [去 AI 味实证手册](https://www.jxxy.net/ai/articles/voidJan-2095423973865746931/)：基于中文对照语料的频率统计，给出各痕迹的 AI/人类倍率、模型指纹和“不能当判据”反表。
- [cn-humanizer](https://github.com/0xtresser/cn-humanizer)、[中文去 AI 味写作指南](https://www.jamecling.com/archives/1175)：中文 18 类模式与替换表。
- [Signs of AI Writing: 12 Patterns With Reproducible Thresholds](https://slopdetector.org/blog/signs-of-ai-writing)：em dash 密度、句长离散度等可计算阈值，及“单项不算，叠加才算”的判断原则。
- 本 skill 自己的语料观察见 [human-samples.md](human-samples.md) 与 [language-notes.md](language-notes.md)。

这些来源里的模型指纹会随模型版本变化（“delve” 2023 年到 2024 年初最多，2025 年已明显减少），
词表按需更新，判断原则不变。
