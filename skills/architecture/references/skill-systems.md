# 技能体系设计与整体审查

在新建技能体系或 review 全部 skills 的架构时读取。对象是任务如何选择、组合与维护
方法；逐篇文字都通顺，只能证明局部表达，不能证明体系覆盖、分工与接合合理。

## 从任务恢复体系

明确体系服务谁、有哪些真实任务，以及通用、项目开发和产品运行等不同接收环境。
全量 review 清点范围内的技能与引用，先看选择描述、主要判断与交付，再深入有争议的
正文和资源。声明范围与排除理由，不能把同名引用当成独立维护副本，也不能漏掉不在
当前展示目录但参与发现或发布的来源。

用足以解释选择的关系记录：技能的任务压力、主要判断、输入与交付、最近邻、维护源
和使用环境。目录与主题标签是导航，不能单独证明技能应该存在或应该独立拆开。

区分可复用方法、工作角色、领域资料、项目操作流程与运行机制。角色可与方法配合，
无需强求同一种结构；资料可作为按需参考，不必独立成为 skill；runtime 保证不能因写成
指导就归技能所有。分类服务于判断，不创建统一模板或强制层级。

## 同时看覆盖与接合

从真实请求走向选择：有用的方法能否发现，最近邻描述能否区分，低风险任务是否被
误导去运行完整流程？再从技能回到任务：是否有独立判断，是否只是别的技能的包装，
是否抢了工具或项目指令的责任？没有消费者的候选保留为候选，不靠假想需求证明覆盖。

方法相似不等于重复。若相同请求需要分别跑两套调查、产出两份相同判断，或同一规则
在两处维护，就检查是否应归并；若对象、失败方式或交付不同，保留独立方法并澄清转向。
具体成立性、载体与表达判断按需使用
[agent-guidance](https://github.com/lidessen/skills/blob/main/skills/agent-guidance/SKILL.md)，整体审查复用其结果，不再发明第二套 skill 准入标准。

引用应说明哪个未决问题需要另一种方法、带入什么、带回什么。相互链接可以成立，
相互要求先完成对方则可能无法开工。检查自动加载与按需选择的区别、资源相对路径、
同名冲突和发布来源；链接有效不证明正文可被目标环境读取或行为已经改善。

整体能力缺口未必需要新技能，可能是缺输入、工具、权限、来源或接线。不得用“建立
总控技能”掩盖这些缺口，也不把复用关系一律做成依赖包管理或永久技能注册框架。

## 取舍与验证

给出保留、改写、合并、拆分、转为 reference 或修正发现入口等选择及依据。执行修改
须保全唯一维护源与实际消费者；来源、示例、元数据和引用一起切换，历史记录注明
当前入口，保留原来判断的语境。不要为了名称对称改变技能职责。

选择能区分最近邻的真实任务，检查发现、选择、按需深入和结果交还。全量架构 review
覆盖所有范围内对象，行为试验可针对有争议的边界，不要求逐技能跑相同脚本。独立代理
的阅读与选择检验可支持路由判断，不能替代真实环境的加载和任务效果观察。

交付整体能力与关系图景、最重要的缺口和重复根因、各对象处置及接合影响、修改与证据。
沿用当前记录，不另建永久技能台账；未核实的加载或效果明确保留未知。
