# 组织与长期协作设计

在设计或 review 团队、岗位、职能协作与决策关系时读取。对象是人怎样共同完成工作，
组织图不是运行事实；岗位名称也不能证明实际权力、能力与资源已经到位。

## 从真实工作看分工

从服务对象、结果与当前困难出发，追踪工作怎样发生、信息在哪里、谁作决定、谁实际
完成、谁接受以及谁承担后果。结合既有约定与具体案例，区分正式安排、实际协作和
未经核实的解释。人的动机或能力不能只凭角色标签推断，敏感判断保留证据范围。

看分工是否支持工作连续：专业知识、沟通负担、资源限制、任务量与变化频率怎样影响
结果？责任有无相应权力和时间，决策者能否取得所需信息？不要把组织问题一律归结为
“执行不力”，也不因存在协调成本就要求所有工作归同一个人。

## 权责、接口与反馈

划清哪些事由岗位独立判断，哪些要共同协商，哪些涉及整体承诺需要集中决定。明确
结果接受、冲突处理与资源分配，不把执行者、建议者、协调者和最终决定者混成一人。
共同讨论不等于共同拥有全部责任；一名负责人也不等于其他人无需提供判断。

接口可以是成果、承诺、协商渠道和反馈节奏，无须把每次交流变成工单、审批或协议。
说明等待、意见冲突、负荷过高或成员离开时工作怎样继续。非正式协作可能有效，先
理解它承担什么，再决定是否需要正式化；不能为了组织图整齐消除实际知识与信任。

比较按职能、产品、项目或其他实际关系组织的得失，不先套矩阵或层级模板。新管理层
或协调岗位必须对应当前无人承担的判断，不为观察进度就增加决策关口。局部效率提高
却加重跨团队等待，或责任下放却不给资源，都不算整体改善。

## 演进与证据

用真实协作案例检查方案，包括日常交付、意见冲突、优先级变化、关键成员缺席与交接。
推演可以指出风险；试行和参与者反馈才能支持实际效果判断。不能从软件依赖图推导
人员应当怎样工作，也不凭组织层数证明效率或公平。

说明变更中的原工作由谁接续、已有承诺与知识怎样保留，哪些安排可以小范围试行。
区分推荐方案、可逆试行与正式制度决定，按用户授权推进；设计任务不自动授权调整
人员、考核、任免或对外发布制度。

若只是安排一次有界任务的多人或多 Agent 分工，按需使用
[divide-and-conquer](https://github.com/lidessen/skills/blob/main/skills/divide-and-conquer/SKILL.md)；长期权责设计仍留在这里。
若缺的是外部组织理论的理解，使用 [research-synthesis](https://github.com/lidessen/skills/blob/main/skills/research-synthesis/SKILL.md)
核对原语境与迁移条件，不把理论流派直接当作本组织的制度。

交付说明工作与现实压力、推荐权责和协作关系、替代方案及代价、过渡与验证、需要
相关参与者确认的事实或决定。不要用岗位说明的数量代替工作链路与整体关系已经闭合。
