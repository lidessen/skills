# 从核心设计核对实现

若任务还要求判断设计是否值得保留、简化或舍弃，可给承担这部分判断的 Agent 使用
[design-steward](https://github.com/lidessen/skills/blob/main/skills/design-steward/SKILL.md)；不要让所有审查者都预设必须找到冗余。
设计取舍与实现是否符合现有契约分别报告，角色倾向不能改写共同设计或正确性标准。

主 Agent 持有已确认设计及其来源，检查当前实现是否履行这些责任。不要让每个审查者重新
发明一份核心，也不要把刚发现的实现机制反过来当成设计要求。只读检查不授权顺手修复。

## 两个方向共同覆盖

- **从实现看覆盖**：用仓库清单、构建入口和注册关系界定待检查对象，包含相关的未提交实现。
  按职责分配代码、测试、配置和启动接线；生成物和外部依赖有明确排除或生成源说明。
- **从设计看链路**：将核心责任追到真实入口、跨模块传递、状态所有者和可观察结果。目录
  都有人看，不代表这条链路有人检查；给每条必要的跨边界链路指定核对者。

在同一任务表中保留对象、对应责任、负责人、证据位置、检查状态和缺口。用户要求逐个实现
检查时，每个范围内的对象都须有状态，不能用抽样冒充全量。分派和阅读不等于核验；结束前
重新比对清单，处理新增、移动和变化的文件。整合时只对受影响结论重新核验。

## 划界示例

以“一次执行从接纳到完成都由节点负责”为设计依据，可以把准入、执行监督、持久化等局部
责任分开审查；主 Agent 或专门的核对者同时追踪“接纳 → 派发 → 执行 → 结果”如何连接。
真实分工取决于当前代码，目录不一致时跨目录追踪，不照此例强分成固定团队。

例如一侧正确拒绝了不支持的请求，另一侧也有正确的请求校验，但公共入口绕过二者，整体
仍不满足设计。应返回绕行入口及调用证据，修复已有接线；不能靠两份“局部通过”结束审查，
也不因此发明第二套权限机制。

## 局部结果与整合

局部报告给出：负责对象的实际覆盖；与设计相符或偏离的结论；可定位的代码/调用证据；
测试或运行观察及其边界；需要邻接方确认的假设。没有发现问题也要交代检查对象和证据。
长日志留在可访问产物中，不把所有文件内容搬进主 Agent 上下文。

主 Agent 核对双向覆盖、冲突和调用链。重点追查跨语言转换、公共入口、配置/注册、状态
交接、错误与取消传播，以及恢复路径；按本任务的核心责任选择，不机械扩成全仓风险清单。
对会驱动修复、重设计或用户决策的关键发现，沿触发条件核对完整相关路径，主动寻找使结论
不成立的分支、已有保障或反例；读到支持结论的几行不等于复核完成。证据绑定所检查的版本，
组件复现、调用链推导与端到端复现分别表达。无法运行时明确停在静态证据，不把测试存在、
mock 成功或多个报告一致写成实际链路通过。

局部发现是待核实的主张，不是最终工作清单。主 Agent 在现有报告中交代每项发现被采纳、
合并、驳回或保留未知的去向；不能因汇总压缩而丢失，也不能把互相矛盾的处置一起交付。
多个局部缺陷若来自同一个接线或职责错误，合并为一个根因及受影响入口；保留独立问题。
整体结论和数量从这些裁决产生，不另造台账。交付按设计责任说明现状、偏离和未知，并附
可追溯覆盖记录，不按报告顺序堆成新的设计文档。
