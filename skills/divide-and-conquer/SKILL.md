# Divide and Conquer

分出去的是可独立完成的贡献，主 Agent 继续对整体结果负责。拆分时就说明结果怎样合起来
满足原任务；子任务全部结束，不代表整体已经完成。分工按真实责任和依赖形成，不预设角色
阵容、人数或层级。

## 先掌握整体，再划出可独立推进的部分

恢复目标、已确认的核心设计、范围与验收依据，并查明现有工具、并发容量、可访问资源和
工作区状态。先做足以划界的探索；未知结构可以先派一个有界探索任务，不盲目均分文件。

复用当前计划或任务表，记录各部分的范围、负责人、依赖、结果位置及验收状态。范围必须
覆盖原任务，交界处也要有人负责。把“分给谁”与“何时可以开始”分开：独立贡献可以并行，
强依赖先后执行，共享写入先确定归属。大任务不必一次拆到底，拆到能独立行动和验收即可。

并行收益要覆盖启动、上下文传递、重复探索和整合成本；关键依赖与整体验证也要留出资源。
只有多条独立工具请求时直接并行调用工具；需要独立判断或隔离大量上下文时才使用子 Agent。

## 给局部工作足够的全局方向

每个委派简短说明：

> 整体目标与不能改变的约束；你负责的局部成果及其用途；权威来源、必要邻接关系和当前版本；
> 可用资源与允许读写的位置；怎样验证；返回产物位置、关键证据、覆盖范围和未决问题。

把共同核心传给每个执行者，细节留在负责者上下文中。不要让每个 Agent 重读全仓，也不要
只给一个目录名。具体工具顺序和局部解法留给执行者；下游依赖的接口与返回要求须清楚。

读可交叉，写要有明确归属；共享文件或服务由指定负责人修改，或使用实际支持的隔离副本
后再整合。主 Agent 不同时改正在委派的对象。全局前提或公共接口改变时，通知受影响者，
确认他们使用的新依据；不能把不同版本的结论直接合并。

## 用现有工具推进和纠偏

实际使用环境提供的创建、派发、消息、状态、等待和中断能力，保存任务标识与输出位置；
不要用角色对白模拟并行，也不为这次工作另造调度框架。不支持并行时按同一分解顺序执行，
说明限制。子 Agent 再拆分也须符合独立性判断，并服从全局资源预算，不能各自无限扩张。

先启动已就绪、能解除依赖或缩短关键路径的工作。主 Agent 同时处理接合、未知边界或其他
独立贡献，不重复子任务。按结果到达逐项验收和释放后续工作；只有真正依赖汇合时才等整批。

用产物、证据和阻塞判断进展。发现跨边界问题或前提被推翻时及时反馈，主 Agent 据此补上下文、
改派、合并或顺序化；正常工作不靠高频催报。等待超时不等于任务失败或写入停止：重派前核实
旧任务状态，必要时停止旧执行者并检查已产生的效果，再交接剩余工作，避免双重写入。

## 合起来验证原任务

检查返回产物与关键证据，按共同约束解决矛盾、遗漏与重复；子 Agent 的结论不能因数量或
措辞肯定就成为事实。主 Agent 聚焦关键主张和交界风险，不把全部局部工作再做一遍。

在合并后的版本上检查接口、共享状态和完整调用路径。局部测试通过不证明接合正确；高风险
或有争议的部分可独立复核，复核者先看原始任务与证据，不预先被告知期望结论。发现问题后
只重开受影响部分及其下游验证；不要将实现缺陷不断升级成新的核心设计要求。

完成需要原范围都有交代、必要接缝已核对、整体结果达到验收要求。读过、检查过、测试通过
和真实运行验证分别报告；受阻或预算耗尽时交付已完成部分与具体缺口，不能改称全部完成。
最终给出整体结论、产物、关键依据与剩余风险，不拼接所有子报告或用 Agent 数量证明成果。

## 按需使用

从核心设计检查全部实现时，读 [implementation-audit.md](references/implementation-audit.md)，
同时处理局部覆盖与跨模块链路。核心本身需要重审时使用 [design-forge](https://github.com/lidessen/skills/blob/main/skills/design-forge/SKILL.md)；
本 skill 组织执行，不替代领域方法，也不自行改变设计决定。

若未决问题是项目或技能体系怎样长期分工、组织怎样分配权责与资源，按需使用
[architecture](https://github.com/lidessen/skills/blob/main/skills/architecture/SKILL.md)。把它形成的责任与接合决定带回当前工作分解；
一次任务的子 Agent 分工不自动成为永久组织，也无需先做长期架构设计。
