# 估计证据与推断边界

先确认**查询时的在售套餐、价格、额外权益和模型/API 费率**；公开用量不能代替这些官方事实。每次运行重查官方页面和估计来源，把来源 URL、当次抓取日、原始观测日及适用条件留在输入和报告中。来源中的金额、tokens/$ 或“等于多少请求”可能已经含有作者的负载和价格假设，先拆出其计算口径。

## 证据梯度

| 层级 | 可支持的结论 | 核对要点 |
| --- | --- | --- |
| 当前官方条款和原厂 API 价 | 在售、标价、分池额度、扣费和明确的限制；能直接换算时给面值 | 地区、档位、计费制度、当期优惠、模型版本、额度是否可叠加及到期日。宣传倍数若无基准，不是 token 配额。 |
| 可复核的原始 usage 日志与额度计量 | 已发生的消耗；有同一窗口计量变化时可估容量 | 开始与结束 meter、耗尽状态、token 分桶、cache 类型/写入时长、模型和模式、窗口起止、API 基准价、账户数、额外用量是否另付；追溯原始数据和方法。 |
| 可核验的第一手 X/社区分享 | 有条件的估计锚点或敏感性场景 | 原帖可访问、日期和套餐/模型/窗口相符，截图能定位出处；自报金额未附 usage 时降低置信。无法打开的转述不能写成已核验原帖。 |
| 明确技术假设与二手汇总 | 低/中/高敏感性；没有可靠锚点时仅作为假设 | 写出完整调用 token mix、cache、扣费倍率、窗口数及来源缺口；不能标成实测或官方保证。 |

`source.class` 使用 `official_current`、`empirical_current`、`stale_empirical`、`explicit_assumption` 或 `theoretical_window`。`empirical_current` 表示原观测能对应**当前**套餐、模型和计费口径，并非“近期”二字就足够。旧套餐/模型、多个账户混合、额外付费、未分清 cache 或作者采用非原厂 API 价时，拆解并校正；无法校正就用 `stale_empirical` 或 `explicit_assumption`，在 `source.assumptions.low/base/high` 写清差异与方向。`model_match:"mismatch"` 的估计不进入排名；混合模型观察用独立 bundle，不能给某一个模型填 `exact`。

## 由观测推断容量

- 未耗尽时，**已观察到的实际消耗**仅证明该窗口至少容纳这些调用，不等于额度上限。若 meter 从某百分比变到另一百分比，按变动比例外推的是**模型化容量估计**，须披露 meter 读数、测量区间、其它 surface 是否共池，以及是否同时购买 extra usage；不能称为“实测打满额度”。真正耗尽且排除额外付费的窗口可作为更强的容量锚点，但仍只代表该账户、版本和技术负载。
- 官方称“5x/20x”、公平使用或未公开 token 上限时，寻找可复核的当前原始测量。将单账户和多账户观测、不同模型 mix、cache 命中率或 API 费率分开成场景，不机械平均为全体通用配额。若来源只报告按其方法算出的每周 API 美元估值，记录为**来源报告的估计**，脚本只负责按明确窗口数折月和计算倍率；不要冒充脚本重算了未取得的 token 日志。
- 周/短滚动窗口只按明确的每月窗口数低/中/高估计，另受官方月 cap 约束。高值可呈现所有可用窗口的**理论上界**，不能把连续全天轮转当典型值或实得；低/中也须有可辩护的窗口解释。此处评估套餐可提供的技术容量，不采集用户个人活跃时间。
- 基础池和当期 flex/bonus/促销池应分别入账，记录额外额度的资格、发放/消耗条件、过期日和 `presence` 低/中/高。证明它们独立可叠加后才相加；“总额度”已经包含基础额度时不能再加一次。API credit 另加到混合模型观测时也要证明观测没有包含该 credit。

结果是**同一种模型及负载下的 API 替代成本**。请求/credit 只能通过其实际扣费或明确的通用调用场景换算；一个 prompt 不等于一次固定长度调用。共享池在不同模型下分别估值但互斥，不把各行求和。任何没有证据支撑的低/中/高值保持未知并说明原因。
