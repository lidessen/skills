# Plan Value Analysis · 订阅计划价值分析

把官方权益、实际扣费规则、精确模型版本、官方 API 价和用户工作负载记录为可追溯的 JSON，交给 `scripts/analyze.py` 计算。**API 等值是替代购买该模型 API 用量的成本，不是订阅返现，也不是跨模型质量分数。** 不用语言模型心算额度、ROI 或排名。

## 何时使用

用户要比较不同厂商、同厂商不同档位，或决定哪些 coding/token plan 值得续订时使用。只要求某一产品现价或功能说明时，直接查官方来源即可；用户要比较模型能力时，需要另立能力标准，不能套用价格排名。

## 建立可信输入

1. 确定地区、币种、统一分析账期、首期与续费、税费、汇率日期，以及用户实际会用的客户端、模型和工作量。一个档位一条 plan；区分现行、旧制、年付保留权益、促销和加购包，不把不同计费制度混成一行。
2. 查**当前官方**计划价、额度、模型清单和扣费规则，再查对应模型的官方 API 价；使用 [官方来源导航](references/sources.md) 定位，打开页面并记录 URL、抓取日期、支持该字段的短证据片段。官网没有披露、资料相冲突或页面不可用时按 [输入契约](references/schema.md) 标为相应状态，未知用 `null`，不能写成零。
3. 核对厂商与产品身份、模型 canonical ID、版本、实际服务 checkpoint、模式和价格适用条件。可变 alias 只有在官方确认其当前落点后才与固定版本合并；同名或同系列不自动算同一模型。独有模型只用**本模型**官方 API 价估值。核对 input、output、cache read/write、长上下文、批处理、时段价是否适用，且 token 桶不能重叠。
4. 记录共享池与独立池、每模型扣费倍率、月/周/滚动窗口、限速并发、公平使用、超额费和允许的客户端或 API。同一权益若同时受短窗口、周与月上限约束，须联合取限，不能拆成可相加的独立额度；脚本无法表达时不得给精确排名。请求数、消息数及“几倍”权益不自动等于 token：须有来源的实际 usage，或明确标记的工作负载场景及敏感性范围。一次提示可能产生多次模型调用，场景应计入完整任务消耗。

## 计算与解释

按 [输入契约](references/schema.md) 准备 JSON，可从 [合成示例](examples/synthetic.json) 改起；该文件**不是现行报价**。合成数据标 `data_kind: synthetic`；正式比较须使用 `data_kind: live`，并为价格、额度、扣费规则、官方 API 价和汇率附 `verified` 字段证据。从本 skill 目录运行下列命令；在其他目录运行时改用 `analyze.py` 的绝对路径：

```sh
python3 scripts/analyze.py INPUT.json --output RESULT.json --markdown TABLE.md
```

检查脚本输出的校验错误、不可比较原因和来源状态，再呈现三个视图：

- **同模型可比榜**：只在 canonical 模型、模式及 API 价条件相同的组内比较；保留客户端和使用限制。
- **各模型自家 API 等值榜**：可列数值与 ROI，但各行模型能力不同，不能据此宣称质量上的总冠军。
- **实际使用／可达价值榜**：按用户需求、有效使用率和活跃窗口约束计算；同时呈现首期、续费、盈亏平衡及适用限制。场景或实测数据的证据等级、置信理由与上下界随结果展示。只有月总需求和活跃窗口次数、没有逐窗口需求分布时，所得可用量只是该场景的上界，不能称为已实现价值。

共享池中“分别把各模型额度花满”只是互斥情景，不能相加。短滚动窗口只按有依据的活跃窗口和需求估值，不能按全天连续轮转充满；要判断实际可达用量，还须检查需求落在哪些窗口，不能把月需求任意搬到空余窗口。没有官方价格、明确额度、可换算 credit 规则或足够的 workload 时，保留未排名和原因；有区间就展示区间，不把估计伪装为精确值。

同产品升级按**增量成本对增量权益**比较，不能把高档位与低档位权益叠加。若用户要同时开几款，必须用确定性脚本把同一份需求分配到各计划及其窗口，才可给组合覆盖、组合 ROI 或“最值得开的前几款”的数值结论。当前脚本若标 `portfolio_analysis.status: not_evaluated`，就明确说组合尚未评估，只能基于单计划行给出带条件的建议；不得把个体行的任务数、额度或成本相加来推测组合结果。**所有派生数字，包括看似简单的加总，都由脚本产生。** 输出推荐时区分计算结论、假设和未量化的体验差异。
