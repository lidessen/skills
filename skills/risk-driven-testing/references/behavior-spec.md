# 稳定行为规格与 YAML 用例

在保存或维护业务行为 KB 时读取。YAML 的知识价值独立于测试层与执行安排：单测足够、不做 GUI、
暂不生成代码都不是省略或删除有用 YAML 的理由。按实际需要保存背景、动作、期望与关联，
简单规则可以保持简式。不因采用 YAML 就强制 E2E、固定配额或执行 DSL。

## 行为比执行表达更稳定

用背景、前提、动作与可观察结果表达合同。定位器、坐标、窗口引用、驱动参数和模型提示属于投影；
URL、协议字段、精确文本若本身是合同，仍保留必要精度。不可从本次产品输出反推正确期望。

按 story（任务主流程）、feature（能力合同）、case（边界或异常）组织：主干步骤进 story，
主线装不下的窗口独立为 case。它们是阅读组织方式，不规定目录、层级字段或测试数量。沿目标项目
已有布局维护可追溯关系，不要求一份 YAML 对应一个 spec，也不为每个执行原子创建用例。一份
YAML 可由多个已有单元 / 集成保障承接，或暂作不执行的 KB；生成哪层代码由真实保障缺口决定。
不必为凑齐三层补一份重复的 feature，也不要求它们逐层引用。

完整例子见 [Google 搜索](examples/google-search/README.md)：以一个小项目展示行为 YAML、原子
动作、流程组装与测试入口的位置和追溯关系，演示输入查询、修改查询，再打开官方文档结果。目录
只是示例，实际项目沿已有布局组织。用例本身写清起点、输入与可观察结果，不为了展示组织方式另拆
feature 或 case。代码是否提取自已观察步骤、是否完成回放，在示例中分别说明；YAML 与代码存在都
不代表当前环境已执行或通过。

## 在项目中放置与追溯

先找项目根、已有行为资料和测试布局，分别确定知识归属与执行入口。行为 YAML 应能独立阅读、
维护和查找，不因暂时没有自动化而放进某个执行脚本的私有目录。没有既有约定时，可以从下面的
布局开始；目录名称只是参考，各测试层和 feature / case 都按实际需要出现。Google 示例只含 E2E：

```text
项目根/
  specs/
    stories/              行为主线 YAML
    features/             按需，独立能力合同
    cases/                按需，边界或异常行为
  tests/
    unit/                 按需，单元测试
    integration/          按需，集成测试
    e2e/                  按需，完整界面流程；Google 示例采用此层
      actions/            可复用的动作步骤
      flows/              动作与断言的组装
      fixtures/           测试准备与本地验证素材
      *.spec.ts           测试入口
```

按目标失败选择代码的位置：规则可落在现有单元测试目录或与源码相邻，模块接合沿集成测试布局，
确需完整路径才放入完整流程测试。已有项目可能以模块、功能或测试层组织，不必为了匹配示例迁移。
准备、登录和设备或浏览器资源沿宿主入口复用；不把凭据或环境状态写进 YAML 和动作代码。

投影中的测试入口或组装代码应指向所依据的 YAML，例如保留相对代码文件可解析的来源路径，或使用
项目已有的可解析链接与元数据；重命名、移动时同步核对。它是追溯线索，不是自动加载、递归执行或
授权，也不需要为此在 YAML 里添加 `ref`。一个行为可由多层测试共同保障，一份测试也可关联多个
行为；已有实现或只有 KB 时不强造一对一文件。具体目录和调用关系见示例项目的 README。

## 字段与投影的关系

- `id`：用语义短名作为阅读和投影追溯锚点，在选定行为库中避免歧义，沿项目已有命名约定。
- `description`：说明这份行为材料负责什么。
- `context`：背景、前提、资源取得方式。可以声明已登录或应用已启动，由独立准备 flow 接回；
  不复制真实凭据，仍核对本例角色、数据和起点。
- `steps`：自然语言 `action` 与可选 `expect`。一个行为动作可由多个执行操作实现，动词不构成
  可执行枚举；执行层 action / agent / decision 不加入这里。
- `expect`：来自需求、协议或有权确认的行为基准，可以是字符串或列表。空缺表示没有额外断言，
  不能据此声称整个行为已验证。
- `lookup`：给 Agent 的自然语言查找线索，不是固定源码绑定。

项目需要时可沿用 `status: manual | automated | stale | obsolete` 表示执行安排的就绪状态。
它不等同于 GUI / E2E，不注册 CI、不授予模型费用或工具权限，也不是本轮通过证据；KB 暂不执行
时可不填，项目已有等价状态时不再建一份。

## ref 只在有阅读价值时使用

先判断读者为什么需要跳转：例如本例依赖一份已有、独立维护的权限合同，而完整复述会复制事实源。
这时才用 `ref` 指向材料并说明关联原因。几句就能写清的前提直接写清；只是主题相同、目录相邻，
或为了展示引用能力，不足以成为拆分与互链的理由。Google 搜索示例不需要 `ref`。

`ref` 是按需阅读线索，不继承前置、不递归展开或执行。不要把单独一个 `ref` 写成动作，也不要把
相关用例列表伪装成有序 `steps`。阅读某个关联 case 不等于本轮必须执行它；选中行为后，仍须根据
它的前提与期望取得实际观察。关联沿项目已有表达维护，不为引用另造统一结构。

路径相对当前文件解析；较大行为库也可按已声明的库根给完整相对路径。相对路径与符号链接不得
越过授权阅读范围；歧义或目标缺失先报告。不把引用可解析当成行为通过。

## 示例的保障边界

Google 示例选择的是用户找文档的任务。期望来自任务目标与
[Google 公开搜索说明](https://support.google.com/websearch/answer/134479)，不是把某次结果列表当作
永久答案。相关结果不必逐字包含所有查询词；排名、摘要、结果数量和页面布局不作固定断言。
示例明确要找 Playwright 官方文档，因此目标域名与文档主题仍须检查，不能只凭页面跳转算通过。

这里操作的是外部搜索产品，没有其内部代码，不能虚构 Google 规则单测来证明网页流程。若目标项目
拥有查询构造、编码或状态更新逻辑，可以用单元或组件测试守住相应部分；它们不证明外部搜索服务
和真实页面接合成立。测试安排留在保障分析与投影中，不混进业务 `context`。

同意提示与起始浏览器由准备流程处理，业务流程不隐藏重登、重开或替用户选择隐私偏好。若遇到
[异常流量验证](https://support.google.com/websearch/answer/86640)、网络不可达或站点拒绝访问，
保留实际阻碍与未验证步骤，不把拦截页、模拟搜索结果或直接访问文档站算作原搜索流程通过。

## lookup 是查找资料，不是固定路径断言

组合使用业务概念、符号、现有测试行为与粗粒度目录定位当前实现。路径可以作线索，但不把它变成
正确性的唯一锚点；重构后应能用其余线索重查。具体定位结果留在本轮工作记录或已有投影里，避免
让稳定行为随每次搬文件更新。

单条线索失效不直接使行为失败；全部失效或存在歧义时先查当前合同、调用与变化。定位失败可能是
测试表达漂移，也可能是按钮误删、权限回归或产品缺陷，不能自动修到绿。行为语义真的变化时先由
有权负责人确认，再同步期望与执行投影。

维护和验证投影时读[执行投影](execution-projection.md)；格式与引用用项目已有解析或静态检查
核对即可，不为这套阅读材料另建通用编译器或校验框架。
