# 局部设计增殖的识别与清理

核对一个局部机制扩张后增加的状态、协议和维护负担，是否仍服务于用户能力或必要保障。
用户所说的“局部设计癌变”，对应的是机制为了维持自身继续制造需求、侵占其他职责的失衡
现象。调查从具体负担开始，允许证据支持删除、归位或保留，不预设病灶或切除结论。

## 从症状找到可核对的关系

先选正在造成负担的一处机制，沿真实调用链找生产者、消费者、权威状态与失败处理者。
范围从当前问题及直接邻接处开始；出现跨模块传播证据时再扩大，不凭一个例子扫描全仓。

| 线索                                                 | 需要核对的事实                                                               |
| ---------------------------------------------------- | ---------------------------------------------------------------------------- |
| 为维护一个关系，持续新增登记、确认、续期、解绑或同步 | 用户工作是否本来就有这个生命周期？关系能否由现有身份、事实或任务上下文表达？ |
| 多个模块为它各存一份状态，再加对账和修复             | 是必要的缓存或投影，还是第二份权威？失效时由谁判断和恢复？                   |
| 一次局部失败需要多个例外、重试或旁路才能继续         | 原错误交给谁就能处理？局部机制是否越权改变了整个任务的完成条件？             |
| 调用方被迫先做额外动作，才能完成原本合法的操作       | 这些动作保护了哪个具体风险？已有授权、事务、版本、预算或反馈为何不够？       |
| 设计的解释越来越依赖内部词汇和修补历史               | 将内部术语去掉后，能否用用户目标与必要约束解释它？                           |
| 所谓简化只隐藏入口，底层仍注册、运行或恢复           | 默认组装、后台工作、存量引用与其他消费者是否仍承担全部成本？                 |

这些只是线索。事务、租约、权限 fence、回执和恢复状态可能承担不可替代的责任；
多入口检查也可能保护不同边界。低频路径要按真实失败后果判断，不能因日常用不到就删除。
临时实验、已经归档的研究和当前默认接线分开看，保留研究不意味着继续接入产品。

## 找到增殖根因

识别时要把“有消费者”“有维护成本”进一步落实为行为差别。围绕候选机制选择能解决当前
疑问的辨别动作，不把下面的方法变成每次必做的流程。

### 将消费者翻译成实际效果

读直接消费点的条件分支和结果，说明这个字段或关系让哪项操作被允许、拒绝、改变或恢复。
继续追到独立的业务承诺：它保护授权、准确版本、提交事实、同步返回还是别的明确能力？
若解释只剩“确保绑定存在”“证明镜像一致”“显示机制已就绪”，再查这些状态怎样服务真实
工作。循环引用自身状态不能独自证明必要性；测试它存在、UI 展示它存在也不自动构成用途。

检查器可以承担独立的完整性保证。要核对它获得什么信息、能发现哪类故障，以及原 owner
为何不能承担这份责任，不能因为唯一消费者是检查器就删除。技术前提也可以来自必要的
实现选择，例如同步读取需要预先初始化、不同进程各自需要缓存。

### 区分业务失败与维护欠账

找出一个具体触发条件：原业务事实、授权和版本仍满足合同，只是候选机制的登记、镜像或
标记缺失，此时系统会怎样？如果合法工作因此被拒绝，追查拒绝条件是否保护了独立承诺，
还是把维护自身状态升级成了业务前置条件。仅隐藏错误或新增旁路不能解决这份关系。

原条件必须核实：缺少设备授权并不等于已获得合法读取权，初始化未完成也不等于同步结果
已经可用。可从源码分支和已有回执推演；只有未知会改变判断时才做隔离验证，不修改线上
状态来制造故障。候选机制缺失时能运行一次，也不足以排除取消、恢复等相关窗口的必要性。

### 检查完整替代路径保住了什么

按 [Design Forge 的减法比较](../SKILL.md#用减法辨明必要性)，用同一输入、权限与完成标准
走一条不依赖候选机制的完整路径，列出真正改变的能力或保障，
不要把调用方暗中接手、人工补偿或提高预算当成机制无价值。必要责任已有明确所有者、
替代路径覆盖相关入口与失败窗口，而被拿掉的只有自维护义务时，才有具体简化依据。
替代方案的缺口应继续核查，不能通过收紧能力或新增状态绕过；局部未知不妨碍修正已有证据
支持的问题。几项分别可删，还须核对一起删除是否失去必要保障。

例如，持续追踪工作和隔离目录并行执行，不必都由 Project 关系承担。若 Task 已有工作事实，
宿主目录 owner 已有身份与授权，Git 已有仓库、版本和工作树事实，可以比较这些 owner 正确
接线后的完整方案，将 Project 保留为有用的组合视图。目录授权、只读限制、执行冲突控制和
原私有资源 owner 仍保留，工具、冻结请求、恢复和 Agent 指导沿同一合同切换。登记减少不证明
实际执行能并行；共享 Harness 的全实例锁仍可能阻断它，须在对应调用链上核对。这个例子说明
必要责任可重新归位，不规定所有产品都去掉 Project，也不将旧 API 不兼容等同于可丢弃存量工作。

将核对结果还原为能说明根因的因果关系：

> 用户要完成什么 → 原来由谁负责 → 新机制改变了什么关系 → 相邻部分因此必须做什么
> → 哪个真实场景受损或成本增加。

新增状态出现得早、多个宿主依赖同一接口，都不证明它制造了多余需求。因果关系仍须接受
反证，报告影响取舍的依据与未知，无需逐段登记。未提供消费者材料时指出最小缺失事实；
已核实消费者只维护机制自身，且独立合同有完整承担路径时，可以支持简化。两者不能混同，
也不能把正常路径不用的恢复状态判为多余。

沿两个方向复核：向上找它服务的真实承诺，向外找为它而新增的字段、API、存储、事件、
工具、UI、prompt、测试和恢复逻辑。同一根因派生的症状一起解释；其中承担独立职责的部分
应保留或归位，不能因为共用一个名字就一并删除。

## 沿接线清理，直到职责重新闭合

有实现授权且判断成立时，从根因处改变关系，将仍必要的责任接回明确的所有者，再清理
只为旧机制存在的消费者和维护路径。API、工具声明、默认组装、状态写入、后台读取、恢复、
UI 与 Agent 指导按实际传播范围一并处理，不保留一层改名后的旧机制。纯评审只交付具体方案
和证据，不越权修改。

存量数据与未完成工作按原恢复合同接续；删除设计不授权删除用户数据。若恢复依赖旧路径，
明确保留排空或查询入口，停止默认新增，并说明退出条件。不要为了清理建兼容框架，也不要
以隐藏状态或丢弃未完成工作来降低表面复杂度。

测试继续围绕用户能力和必要保护。只验证旧机制内部动作的测试随旧合同退出；保护独立业务
保证的测试保留或改由新的责任入口验证。不能通过删失败测试、换更容易的输入或降低完成
标准制造通过。检索剩余引用时区分正式入口、合法其他消费者、恢复入口与历史研究，不能
要求关键词全仓零命中。

验收看原任务与必要保护是否仍成立，原先为维护机制而产生的义务是否消失。跨模块验证接合处，
Agent 采用效果另看真实行为。交付说明根因、保留的责任、移除的负担和证据；职责与受影响
路径闭合后结束，允许撤回误判。这是一种按需调查方法，不新增评分、台账或强制审查阶段。
