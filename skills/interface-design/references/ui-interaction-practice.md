# 视觉质感与组件取舍

用于新做、改版或打磨 UI。默认只解决本次最明显、影响最大的少数问题，不要求每项检查都走一遍。

## 看整页：哪里显得粗糙或失衡？

有实际页面时先看整屏，判断视觉重点是否明确、主次是否合理、空间是否平衡。再看最影响质感的细节：对齐与比例、字体层级、留白节奏、颜色、边框和阴影、图标及控件的精度。

不要停在“丑”“不精致”或“间距不对”。指出具体位置和关系，例如“导航、标题和主内容权重相同，第一眼找不到任务入口”；再决定要重组层级，还是修正排版、对齐或组件细节。先修构图和层级，再打磨像素；不靠加渐变、卡片和装饰掩盖结构问题。

## 看每个元素：它帮用户完成什么？

对当前改动范围内显眼的组件和控件，问：

- 它支持哪个任务、判断或下一步动作？
- 它是否重复已有信息或操作，反而增加选择和视觉噪音？
- 它占用的空间和视觉权重，是否匹配它带来的价值？

有明确用途就保留；作用重叠时考虑合并；有用但次要时降低权重；确认没有实际作用后，才考虑移除。不要只因组件少用就删掉低频但重要的操作，也不要把所有内容都塞进卡片、标签或按钮。

## 看相关交互，再复看改动

只检查本次涉及的控件：用途是否看得懂、前置条件是否满足、操作是否自然、操作后有没有清楚反馈。依赖数据或服务的页面要区分真实空态与加载/读取失败，避免提供当前无法完成的操作入口。等待、错误、撤销、取消等状态，在涉及异步、破坏性或不确定动作时再检查；AI 输出、辅助技术、键盘等专项检查也按问题触发。

修改后有运行页面就重新打开，使用真实内容检查整页，并亲自走一遍本次改动涉及的操作。尽量用相同视口对照；无法运行时说明只判断了静态稿或代码。无需每次都做多方案比较或组织用户测试；只有方向难判断、影响较大且现有证据不足时，再做原型比较或找目标用户观察。

评审和交付说清三件事：哪里粗糙或失衡、元素为何有用或多余、改后从页面中观察到什么。区分实际观察和设计判断，不评分，也不把完整检查表变成门禁。

## 调研来源（按需阅读）

这些来源用于校准，不要求每次全部重读。产品博客和社交平台帖子不等同于独立效果验证。

- [Anthropic：Improving frontend design through Skills](https://claude.com/blog/improving-frontend-design-through-skills)：模型容易趋向常见安全样式；提供明确设计原则和项目语境。产品方文章，不证明某一种风格更好。
- [Vercel：AI-powered prototyping with design systems](https://vercel.com/blog/ai-powered-prototyping-with-design-systems)：给模型组件结构、样式和组合关系，不只给色彩 token。产品方文章，不需要照搬其技术栈。
- [Google Design：Material 3 Expressive 研究](https://design.google/library/expressive-material-design-google-research)：对比、形状和尺寸可以帮助突出重点，但偏离熟悉模式也可能伤害可用性；具体结论依赖其产品与研究条件。
- [X：Piyush Agarwal 的页面改进 skill](https://x.com/doerpiyush/status/2032697698567254427)：作者分享从诊断到逐项修饰页面的做法。个人经验，主要谈视觉细节，没有交互效果验证。
- [Reddit：Actual AI Design Workflows in 2026](https://www.reddit.com/r/UXDesign/comments/1tf2yea/actual_ai_design_workflows_in_2026/)：讨论按用户和具体目标约束 AI 评审；参与者也提到模型反馈会出错。个人经验，不代替实际使用观察。
